# Phase 16 — UI Design Contract

> Visual and interaction contract for the Phase 16 state/payload-facing surface. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none; reuse the existing static HTML/JavaScript renderer patterns |
| Icon library | none; use text labels, borders, and existing status marks so state is never color-only |
| Font | Arial, Helvetica, sans-serif (existing World Cup dashboard contract) |

**Stack and boundary:** R generates static HTML/JSON payloads and the browser renders them. Phase 16 owns state-shaped payload fields and the visible status contract; Phase 17 owns shared dashboard composition, responsive filters, data-credit treatment, refresh operations, and browser smoke checks.

**Existing visual patterns to preserve:** `#f7f6f2` page paper, white panels, thin `#d8d8d8` rules, compact tabular surfaces, blue top rules for primary metrics, native `<details>` disclosures, and text-first status labels from `docs/wc2026/index.html`.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Status-mark gaps, inline metadata gaps, compact table padding |
| sm | 8px | Warning contents, row groups, badge padding, disclosure contents |
| md | 16px | Default panel padding, banner padding, section spacing |
| lg | 24px | Competition state header and major section padding |
| xl | 32px | Layout gaps between state summary, ledger, and topology surfaces |
| 2xl | 48px | Major page-level separation when the Phase 17 shell places sections vertically |
| 3xl | 64px | Page-level spacing only; not used inside the Phase 16 state surfaces |

Exceptions: icon-free status marks use a stable 18px square only when the existing renderer needs a compact marker; interactive disclosure and link targets must retain at least 44px total hit height. Do not introduce new spacing values between these tokens.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 700 | 1.2 |
| Heading | 20px | 700 | 1.2 |
| Display | 30px | 700 | 1.1 |

Use tabular numerals for ranks, counts, dates, capacities, and probabilities. Use the existing compact 12px label treatment for source IDs, ruleset versions, status reasons, and timestamps. Long source URLs and hashes wrap or move into a disclosure; never force a table column wider than its container.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f7f6f2` | Page background and inactive whitespace |
| Secondary (30%) | `#ffffff` | Header, state summary, ledger, topology, and lineage panels |
| Accent (10%) | `#3573a8` | Active state indicator, primary section rule, accepted/available emphasis, and the `View qualification rules` action |
| Destructive | `#b23a2f` | Blocked refresh or invalid accepted-candidate state only; never used for ordinary unavailable data |

Existing semantic colors remain allowed for their established meanings: `#d29d2b` for warning/revision attention and `#3b8754` for resolved positive outcomes. Use border and text labels with these colors; do not use color as the sole status signal.

Accent reserved for: the active lifecycle state, the primary state-summary rule, the current accepted bundle marker, links/actions that open rules or lineage detail, and resolved qualification emphasis. Do not wash every interactive element blue.

**Warning hierarchy:**

1. `blocked` or `source_revision_pending`: full-width top banner with a 3px gold or red left rule, explicit label, and the last accepted snapshot identity.
2. `unresolved`, `insufficient_source`, `host_place_unresolved`, `unresolved_external_eligibility`, or `unsupported_topology`: section-level warning row with a gold left rule and reason text beside the affected table/section.
3. `source_confidence` and refresh metadata: quiet muted metadata in the state summary or lineage disclosure; never compete with the primary content.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `View qualification rules` |
| Empty state heading | `EURO qualifying is awaiting the official draw` |
| Empty state body | `Official groups and the schedule are not available yet. The draw is expected on 6 December 2026. Forecasts will appear after a complete official draw-and-schedule bundle is accepted.` |
| Error state | `Qualification outputs unavailable. The accepted source or rules bundle is incomplete or blocked. The last accepted state remains visible; no groups, fixtures, standings, or probabilities are fabricated.` |
| Destructive confirmation | `None — Phase 16 exposes no destructive user action. Candidate bundle replacement is a validated backend operation; the UI only reports its status.` |

Status labels must be human-readable while retaining machine-readable values in the payload: `Pre-draw`, `Active`, `Refresh pending`, `Blocked`, `Unavailable`, `Unresolved`, and `Available`. Use `Unavailable` or `Unresolved`, never `0%`, for suppressed probability outputs.

## Phase Surface Contract

### State summary

Render one competition-level state summary before any qualification data. It must show, in this order:

1. Lifecycle status: `pre_draw`, `scheduled`, `in_progress`, or `complete`, with a visible human label.
2. Forecast status: `pre_draw`, `available`, `unavailable`, `blocked`, or `suppressed`.
3. Official draw date: `6 December 2026` while pre-draw; after activation retain the draw date as historical metadata.
4. Last refresh time and accepted bundle ID.
5. Source confidence and whether the visible state is official or reviewed fallback.
6. The primary warning, if any, with its reason enum translated into plain language.

The state summary is payload-facing and must be stable across pre-draw, active, and blocked states. It must not imply that a date alone activates the edition.

### Pre-draw and empty sections

Before a complete official draw-and-schedule bundle is accepted:

- Keep groups, fixtures, standings, results, qualification ledger, topology, and probability collections schema-valid but empty.
- Show the documented empty-state copy for the main qualification surface.
- Pair each empty collection with an explicit `pre_draw` or `unavailable` status and a reason such as `awaiting_official_draw` or `schedule_not_accepted`.
- Show no projected teams, placeholder groups, bracket slots, fixture cards, scorelines, or fixture-level/qualification probabilities.
- Show the edition-level forecast status and reason instead of rendering disabled-looking probability cells.

The empty surface should read as an intentional waiting state, not a broken load. Empty collections reserve their normal section heading and structure so activation can populate them without changing the payload contract.

### Accepted post-draw state

After the activation gate passes, expose:

- Official groups and fixtures keyed by stable `team_id` and `fixture_id`.
- Standings with explicit rank, played, points, goal difference, rule status, and tie-break evidence fields available to the renderer.
- Fixture forecast availability only for confirmed kickoff rows admitted by the forecast contract.
- Qualification outputs as status-bearing rows, not as a single opaque probability field.
- Source bundle ID/hash, ruleset version/hash, model release identity, and state cutoff lineage.

An initial active bundle may have zero completed results. In that case show official groups and scheduled fixtures, a `No completed results yet` note for standings, and do not mark the edition unavailable if the activation bundle itself is valid.

### Qualification ledger

The qualification ledger is the primary Phase 16 output surface. Render it as a compact, horizontally scrollable table on narrow containers and a full table on wide containers. Preserve one ordered allocation row per stage:

- Direct group winner.
- Best runner-up.
- Host reservation and host-slot consumption.
- Remaining runner-up play-off place.
- Nations League A-C entrant.
- League D fallback.
- Broader ranking fallback.
- Final play-off topology placement.

Every row must expose or make discoverable: team display name and stable identity, stage, qualification status, host association/slot where relevant, `consumes_capacity`, probability when available, status/reason, source lineage, and ruleset lineage. Never collapse a host direct qualifier into a generic direct row: host treatment stays visible in this main table.

Required status vocabulary for this surface: `direct`, `host_reserved`, `host_reserved_occupied`, `host_reserved_unused`, `host_place_unresolved`, `playoff_eligible`, `unresolved_external_eligibility`, `unsupported_topology`, `suppressed`, and `unavailable`.

### Host-place treatment

Show host slots as explicit conditional rows with a stable slot number, association, occupancy status, and capacity effect:

- `Occupied`: show the team and the direct-qualification or play-off event that consumed the slot.
- `Unused`: show the slot as released into the play-off allocation and display the remaining capacity.
- `Unresolved`: show the slot and association, but suppress team probabilities and display the exact missing rule/source reason.

Use a small gold `Host place` label beside the team/status text and a plain-language note such as `Counts once toward host capacity`. Do not rely on a star, color, or tooltip alone.

### Best runners-up and play-off topology

Keep the topology summary adjacent to the ledger because topology depends on host-slot usage. Display the resolved branch as a compact rules table:

| Reserved host slots used | Entrants | Structure | Places |
|--------------------------|----------|-----------|--------|
| 2 | 8 | 2 single-leg paths of 4 | 2 |
| 1 | 12 | 3 single-leg paths of 4 | 3 |
| 0 | 8 | 4 seeded-versus-unseeded home-and-away ties | 4 |

Mark the current branch with the blue accepted-state treatment and the text `Current topology`. If topology, draw constraints, or required eligibility is incomplete, replace the branch highlight with `Play-off format unresolved` and the reason. Do not render a guessed bracket or probabilities for an unsupported shape.

Best-runners-up rows must show the official ranking stage, counted/excluded match evidence, rank, and status. If direct qualification or host allocation is incomplete, show `Best runners-up unavailable until direct and host allocation is resolved` instead of an ordering based on partial data.

### Source and rules lineage

Provide a native `<details>` disclosure titled `Source and rules lineage` on the state summary and repeat a compact lineage reference in the ledger/topology headers. The disclosure must include:

- Accepted source bundle ID and source confidence.
- Retrieval/refresh timestamp.
- Ruleset version and full ruleset SHA-256.
- Source artifact IDs or URL lineage for the visible result.
- State/forecast/model release identity and cutoff when probabilities are present.
- Revision or fallback note when the visible state is not the newest candidate.

Use monospace or tabular numerals for IDs/hashes, allow wrapping, and keep the default disclosure collapsed after the primary status is understood. This is lineage, not the Phase 17 collapsed data-credit treatment.

### Revision, blocked, and unavailable behavior

When a replacement source/rules bundle is being validated or fails validation:

- Keep the last accepted state and its identity visible.
- Add a top warning: `Refresh pending — showing the last accepted EURO snapshot` or `Refresh blocked — showing the last accepted EURO snapshot`.
- Include the candidate failure reason in the warning disclosure, but do not expose candidate groups, fixtures, standings, ledger rows, or probabilities.
- Keep `blocked` as an overlay; do not rewrite the accepted lifecycle state as if it were absent.

For unresolved input, keep the affected section visible with its normal heading, a status label, the reason, and empty/suppressed rows. Do not turn missing values into zeroes or generic errors.

### Interaction contract

- Use the existing dashboard's tabs or section navigation for entry into qualification content; Phase 16 does not add a new navigation model.
- `View qualification rules` opens the rules/topology disclosure or an existing rules section in the same static page. It does not trigger a refresh or mutate data.
- Use native `<details>` for `Why unavailable`, `Source and rules lineage`, and topology/ranking evidence disclosures. Summary text must be keyboard-focusable and have an obvious open/closed state.
- Ledger rows may expose evidence through disclosure or a stable row detail target, but selection must not change the accepted dataset or hide warnings.
- Warnings remain visible while users inspect the ledger, host slots, or topology. Do not bury a blocking/revision warning behind a tab.
- Status text, reason text, and numeric values must remain available to assistive technology; visual marks are supplementary.

## UI Considerations

Applicable state considerations resolved: 8 taxonomy categories covered, 0 backstop, 0 unresolved. Probe audit: 22 applicable edges, 22 explicit, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| {empty} | Qualification ledger, groups, fixtures, standings, topology, probabilities | ✅ covered | Pre-draw collections remain schema-valid and empty; the documented awaiting-draw copy and `pre_draw`/`unavailable` reason are shown, with no fabricated teams or probabilities. |
| {loading} | Accepted-bundle refresh/status summary | ✅ covered | Refresh-in-flight is represented as `Refresh pending` while the last accepted snapshot remains visible; no candidate content is rendered. |
| {error} | Warning stack, ledger, topology, probability sections | ✅ covered | `Blocked`, `unresolved`, `insufficient_source`, and unsupported-topology reasons render as explicit text with the last accepted fallback where available; affected derived rows are suppressed. |
| {populated} | Active groups, scheduled fixtures, qualification ledger, topology table | ✅ covered | A complete official bundle renders real groups and fixtures; the ledger and current topology expose direct, host, runner-up, Nations League, and play-off stages. |
| {partial} | Initial active bundle, host ledger, best runners-up | ✅ covered | Zero completed results are valid after activation; host slots and runners-up remain status-bearing and unavailable until their required inputs resolve. |
| {overflow} | Ledger, topology evidence, source URLs/hashes, long team names | ✅ covered | Tables scroll horizontally within their surface, long identifiers wrap in disclosures, and team text wraps or truncates without changing column geometry. |
| {zero-one-many} | Host slots, warnings, topology branches, ledger stages | ✅ covered | Zero host slots, one host slot, and two host slots retain explicit slot rows; one or many warnings stack by severity; the topology table always preserves all three official branches. |
| {long-text} | Warning reasons, source/rules lineage, team and association names | ✅ covered | Text wraps within bounded panels; hashes and URLs use breakable text; no long source or reason string may overlap adjacent status or table content. |

Open UX considerations owned by the shared dashboard phase: full responsive filter behavior, print behavior, broad WCAG audit, offline/real-time refresh affordances, collapsed data credits, and browser smoke coverage.
