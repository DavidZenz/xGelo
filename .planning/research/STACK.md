# Project Research: Stack for UEFA Competition Dashboards

## Existing foundation

- R remains the analytical and orchestration language.
- `targets` already handles the reproducible data/model graph.
- The World Cup dashboard is a static HTML/CSS/JavaScript payload generated by R.
- The existing release layer already provides calibrated 1X2 probabilities, score distributions, release manifests, and integrity checks.
- `testthat` is the established validation framework.
- macOS `launchd` already provides the hourly refresh and publish trigger.

## Recommended additions

### HTTP and snapshot acquisition

- Use `httr2` for bounded, rate-limited requests and explicit response validation.
- Use `jsonlite` for structured payloads and `xml2`/`rvest` only behind a source adapter when an official export or stable HTML table is actually available.
- Do not spread UEFA page parsing through model or dashboard code. A UEFA adapter should be the only component that knows the current page or endpoint shape.
- Persist the exact response bytes, request URL, retrieval timestamp, HTTP metadata, and SHA-256 hash in a local snapshot manifest.

### Competition rules

- Implement rules as small, pure R functions with separate registries for `unl_2026_27` and `euro_2028_qualifying`.
- Keep standings, tie-breakers, promotion/relegation, qualification, and play-off path formation independent from the renderer.
- Treat regulation text as a versioned input. A ruleset change must invalidate downstream projections rather than silently changing historical output.

### Dashboard delivery

- Reuse the existing static dashboard engine and browser-safe JSON payload pattern.
- Add shared renderer components for header metadata, competition state, standings, form, fixtures, match cards, forecast explanation, probability tables, and data credits.
- Publish two stable entry points, for example `docs/nations-league/` and `docs/euro-2028-qualifying/`, with separate output directories and manifests.
- Keep generated score distributions and large simulation artifacts out of Git history. Publish compact consumer payloads and manifests; retain large intermediates locally or in an explicitly managed artifact store.

### Refresh and operations

- Extend the existing `launchd` pattern to one orchestration script that refreshes both competitions as an atomic batch.
- Stage source snapshots and derived outputs before replacing the last successful public bundle.
- Run source validation, rules validation, model/release validation, dashboard smoke checks, and tests before commit/push.
- Preserve fail-closed behavior on dirty worktrees, branch divergence, incomplete sources, failed tests, or failed output hashes.

## Avoid adding

- A new frontend framework for this milestone. The current static dashboard is already the deployment surface.
- A paid football-data provider as a required dependency.
- A live database or server API before the source and rules contracts are stable.
- Automatic scraping of restricted match-statistics providers for competition state.

## Source and library risks

The official UEFA pages expose the authority for fixtures, groups, standings, and regulations, but the public pages inspected for this research do not document a stable developer API. The implementation should therefore use a replaceable adapter, keep request volume low, and retain manual audited snapshots as a supported fallback.
